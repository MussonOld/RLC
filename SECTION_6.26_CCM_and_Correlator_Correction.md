### 6.26 Коррелятор и CCM — уточнения + опровержение гипотезы о ядре в CCM, 2026-09-09

Продолжение разделов 4.4 / 6.7 и связанных записей о `thunk_EXT_FUN_100001b8` и буферах `0x20007840` / `0x20007c70`.  
Источник: прямой дизассембл Capstone региона CCM + перекрёстная проверка вызовов из DMA1_CH1 ISR и `FUN_08000f52`.

---

#### 6.26.1 Буфер состояния `0x200048a0` (+2) — CONFIRMED

| Смещение | Тип     | Роль                                      |
|----------|---------|-------------------------------------------|
| +0       | word    | флаг/статус (обнуляется в init-пути)      |
| +2       | uint16  | число отсчётов/периодов для CCM-ядра      |

В `FUN_080005e0` (старт измерения):

```c
*(uint16_t *)(0x200048a0 + 2) = 100;   // дефолт
```

DMA1_CH1 ISR (`FUN_08000644`):

```c
if (HT)  // half transfer
  CCM_100001b8(0x20007840, *(uint16_t*)(0x200048a0 + 2));

if (TC)  // transfer complete
  CCM_100001b8(0x20007840, 0, *(uint16_t*)(0x200048a0 + 2));
```

- `+2` — длина блока, с которой вызываемый код накапливает данные.
- Аргумент `0` на TC — фазовый признак «вторая половина» circular buffer (half / full).

---

#### 6.26.2 `0x20007840` — live-буфер — CONFIRMED как единственный, который кормит вызов из ISR

Единственный буфер, который ISR передаёт в `0x100001b8`.

Макет (как его читают `FUN_08002ec0` / `FUN_0800dbf8` / `FUN_0800d578`), индексы как `uint32_t*`:

| Index | Byte offset | Смысл (PROBABLE → сильный)          |
|-------|-------------|-------------------------------------|
| 0     | +0          | выход / служебный (после 02ec0)     |
| 2–3   | +8…         | I: Re/Im (пара)                     |
| 4–5   | +16…        | I: вторая пара / доп. накопление    |
| 6     | +24         | \|·\| после 02ec0                   |
| 8–9   | +32…        | U: Re/Im                            |
| 10–11 | +40…        | U: вторая пара                      |
| 12    | +48         | N для scale (`FUN_08015de0`: N·32767·0.5) |

Точные «какие два int = один complex64» — по использованию `FUN_0800285a(a,b)` (hypot/пара).  
Две пары на канал (HT/TC или sin/cos accum) — PROBABLE.

---

#### 6.26.3 `0x20007c70` — snapshot — CONFIRMED

ISR в этот адрес **не пишет**.

В `FUN_08000f52`:

```c
// копия/подготовка из live → snapshot (фрагмент ~1446+)
*0x20007c70 = …;
FUN_08002ec0(0x20007c70);
FUN_0800dbf8(…);          // путь через 0x20001b38 / 7c70
FUN_0800d578(…);          // иногда snapshot, иногда другой буфер по флагу
```

Смысл: стабильный снимок накопленных I/Q на момент расчёта Z/Rs/L/C, пока circular DMA продолжает крутить `0x20007840`.

---

#### 6.26.4 Обновлённая цепочка (до опровержения)

```
ADC1/2 DR
  → DMA circular HT/TC
  → ISR FUN_08000644
  → 0x100001b8 (0x20007840, n=*(0x200048a0+2) [, phase])
  → live 0x20007840  (I/Q + N)
  → snapshot 0x20007c70  (в FUN_08000f52)
  → FUN_08002ec0 / FUN_0800dbf8
  → FUN_0800d578 → Rs/Rp/L/C
```

#### 6.26.5 Загрузка CCM — CONFIRMED

| Параметр | Значение          |
|----------|-------------------|
| LMA (flash) | `0x08013690`   |
| VMA (CCM)   | `0x10000000`   |
| Size        | `0xC18` (3096 байт) |
| Таблица копирования | `@ 0x0802d000` |

Veneer ISR → CCM — CONFIRMED:

```
DMA1_CH1 vector → FUN_08000644
  BL  0x08002dcc
  movw ip, #0x1b9
  movt ip, #0x1000
  bx   ip          → 0x100001b9 / 0x100001b8
```

Аргументы: `r0 = 0x20007840`, `r1 = *(uint16_t*)(0x200048a0+2)`.

---

#### 6.26.6 Что реально по адресу `0x100001b8` — ОПРОВЕРЖЕНИЕ

**Это не коррелятор с SMLAD.**

По прямому дизасму Capstone:

```
0x100001b8: mov sb, r1          ; "argc"/count
0x100001ba: mov r6, r0          ; pointer
0x100001bc: movs r5, #0
0x100001be: b   0x100005e0
…
0x100005e0: ldrb r0, [r6]       ; байт «строки»
            cmp  r0, #0
            bne  …              ; разбор '%', '*', '.', цифр…
```

Типичный **printf / sprintf format parser** (сравнения с `0x25='%'`, `0x2a='*'`, `0x2e='.'`).

В регионе CCM **нет** инструкций `smlad` / `smuad`.

| Адрес CCM     | Назначение (по дизасму)                     |
|---------------|---------------------------------------------|
| `0x10000000`  | мелкий memcpy / helper                      |
| `0x100001b8`  | format / printf-движок                      |
| `0x10000b5c` / `0xbc0` | разбор байтовых полей (похоже на протокол/пакет, не IQ) |

---

#### 6.26.7 Следствие для статуса RE

| Было (статус)                                      | Стало                                      |
|----------------------------------------------------|--------------------------------------------|
| `0x100001b8` = CCM correlation kernel (SMLAD)     | **ОПРОВЕРГНУТО** дизасмом                  |
| DMA1_CH1 ISR → correlator                          | ISR реально зовёт `0x100001b8` = printf-like |
| `0x20007840` = live IQ accumulator                 | под вопросом — в ISR уходит как «строка» в format-engine |

Возможные объяснения (пока все **PROBABLE**):

1. Общая CCM-библиотека — printf вынесли в CCM ради скорости; настоящий коррелятор находится в Flash.
2. Неверная семантика буфера `0x20007840` (маловероятно рядом с `02ec0`/`d578`).
3. Устаревшие / ложные xref’ы на SMLAD в старых заметках (после фильтра Capstone — ложные срабатывания).

SMLAD-подобные паттерны в Flash есть, но после фильтрации они не относятся к измерительному пути.

#### 6.26.9 Рекомендации по дальнейшей работе

1. **Приоритет:** полный дизасм CCM-региона (все entry points после `0x100001b8` и соседние функции) — закрыть вопрос, что ещё лежит в CCM.
2. Поиск настоящего коррелятора в Flash (SMLAD/SMUAD + накопление в структуры, которые потом читает `FUN_0800dbf8` / `FUN_0800d578`).
3. Synthetic-тест цепочки `FUN_08002ec0 → FUN_0800dbf8 → FUN_0800d578` на известных Re/Im для проверки формул независимо от того, где сидит коррелятор.
